# 書籤功能建置規格

> 這份文件提供給脫離 Lovable 後的新專案 AI agent，作為「書籤／願望清單」功能的建置提示詞。
>
> 新專案的原型 HTML、視覺風格、版面配置與既有元件系統是最高優先。以下功能需求需要套用到新原型，而不是照搬本專案目前的 UI 或技術檔案結構。

## 任務目標

在服飾管理網站中建立一個私人「書籤」頁面，讓使用者儲存想購買或稍後查看的服飾商品。

使用者會從品牌或電商網站複製商品頁網址，貼到書籤頁面建立書籤。系統嘗試從商品頁讀取商品資訊，使用者確認或補充資料後儲存。每筆書籤應以商品卡片呈現，點擊後可前往原商品販售頁面。

## 重要 UI 原則

1. **以新原型 HTML 為準**
   - 先讀取新專案提供的原型 HTML、CSS、元件與路由。
   - 沿用新原型的色彩、字體、間距、圓角、陰影、按鈕、表單、dialog/modal、toast 與 responsive layout。
   - 不要直接複製舊專案的 Lovable/TanStack UI。
   - 不要為了實作功能而重建或覆寫整個既有頁面。

2. **保留既有介面風格**
   - 書籤頁要像衣櫥中的商品卡片，而不是單純的資料表格。
   - 桌面與手機版都必須可操作。
   - 商品圖片是卡片的主要視覺內容。
   - 卡片要清楚顯示商品名稱與辨識款式所需的資訊。

## 使用者流程

### 建立書籤

1. 使用者進入「書籤」頁面。
2. 點擊「建立書籤」或原型中對應的新增操作。
3. 顯示建立表單，第一步要求貼上商品頁網址。
4. 使用者貼上公開的服飾商品頁 URL。
5. 系統驗證 URL 必須是有效的 `http` 或 `https` 網址。
6. 系統嘗試從商品頁讀取 metadata：
   - 商品名稱
   - 品牌
   - 商品圖片
   - 價格
   - 貨幣
   - 商品描述
   - 商品頁網域
   - 可取得時的顏色、款式或 variant 資訊
7. 將讀取結果填入可編輯的確認表單，預設只顯示必要資訊；非必填欄位依下方「簡潔表單與展開互動」規則收合。
8. 如果自動讀取失敗，仍應允許使用者手動補充資料與上傳商品圖片。
9. 使用者確認或修改資料後儲存。
10. 儲存成功後，書籤出現在列表最前方。

### 簡潔表單與展開互動

新增畫面以簡潔、乾淨、低輸入負擔為優先，採漸進展開，避免一次顯示所有欄位。

1. **貼上網址階段**：只顯示商品網址輸入框、「繼續」及取消操作。點擊繼續後驗證並讀取商品資訊；讀取中顯示載入狀態。讀取失敗仍可進入手動填寫的確認畫面。
2. **確認階段**：主要顯示商品名稱、商品圖片預覽、「補充更多」入口與「儲存書籤」按鈕。已輸入的商品網址以精簡來源資訊搭配「修改網址」入口呈現，不重複佔用大型輸入區。
3. **有需要才展開**：「補充更多」預設收合，使用文字按鈕搭配展開箭頭，避免做成另一個高強度主按鈕。展開後原位置顯示「收合商品資訊」，再次點擊可收起。
4. **展開內容**：品牌、顏色／款式、尺寸、價格、貨幣、商品描述與備註；全部為選填。來源網域由商品網址取得，不要求使用者填寫。
5. **可直接儲存**：只要有效商品網址、商品名稱及可用圖片已備妥，就能儲存；不得要求使用者先展開、瀏覽或填寫非必填欄位。
6. **資料不因收合消失**：自動取得及手動輸入的選填資料在收合後仍保留，儲存時一併寫入。收合區已有資料時，可在入口旁顯示簡短「已有資料」提示，不再列出整排詳細欄位。
7. **不自動打開選填區**：取得 metadata 或抓取失敗都不應自動展開全部選填欄位；必要的名稱或圖片缺漏在主要區域直接提示。若提交時某個已填的選填值格式有誤，則展開對應區域並定位錯誤，方便修改。
8. **展開不重置表單**：切換展開／收合不清空已填內容、不重新解析網址，也不改變儲存按鈕的用途。修改網址後須明確重新讀取；新的解析結果不得無提示覆寫使用者已手動修改的資料。
9. **編輯保持一致**：編輯既有書籤時沿用相同收合設計，保留所有既有選填資料。使用者未展開或未修改的欄位不可在更新時被清空。
10. **手機與鍵盤操作**：展開入口可用鍵盤操作並標示展開狀態；展開後表單可正常捲動及操作儲存，沿用新原型的版面規範。

展開入口文案定案為「補充更多」。商品資訊補充與主要儲存操作須有清楚的視覺主次。

### 圖片為必要資料

每筆書籤必須有商品圖片，不能建立沒有圖片的書籤。

- 優先使用商品頁 metadata 取得的圖片。
- 如果商品頁沒有讀取到圖片，使用者可手動貼上圖片 URL，或從裝置上傳圖片；兩種方式擇一即可。
- 外部圖片 URL 必須是有效的 `http` 或 `https` URL；上傳檔案須驗證圖片格式與大小，並使用新專案既有的檔案儲存方式。
- 儲存按鈕在沒有可用圖片、圖片 URL 格式錯誤、外部圖片預覽載入失敗，或圖片上傳失敗時必須阻止提交，並顯示清楚錯誤訊息。
- 商品名稱下方為商品圖片區。有可用圖片時只顯示預覽與低強度的「更換圖片」入口；點擊後才提供「貼上圖片網址」與「上傳圖片」兩種方式，不常駐顯示圖片網址輸入框。
- 沒有可用圖片或圖片載入失敗時，圖片區直接提供補圖入口與簡短提示，不藏在選填區。選擇貼上網址才展開網址輸入框；選擇上傳則開啟檔案選擇。標示「商品圖片（必填，擇一提供）」，選用上傳圖片時不需填圖片網址。
- 表單必須提供圖片預覽；使用者可以更換目前圖片。
- 儲存後若外部圖片日後失效，卡片應顯示替代畫面並提供更換圖片入口，不應讓既有書籤消失。

### 商品款式與顏色

商品 URL 不一定能表示使用者選擇的顏色或款式。相同商品頁 URL 可能包含多個顏色、尺寸或 variant，因此不能只依 URL 推測使用者意圖。

建立表單的「補充更多」區必須提供以下可編輯欄位：

- `顏色／款式`：選填，例如「黑色」、「短版」、「連帽款」
- `尺寸`：選填，例如「M」、「38」

如果商品頁 metadata 能取得顏色、款式或尺寸，先填入表單讓使用者確認；讀取不到時保持空白，讓使用者自行輸入。

同一商品允許建立多筆不同款式的書籤，例如：

- Oversized T-shirt／黑色／M
- Oversized T-shirt／白色／M
- Oversized T-shirt／黑色／L

### 點擊商品

- 點擊商品卡片或卡片上的外部連結操作，開啟 `productUrl`。
- 使用新分頁或依新原型既有的連結行為處理。
- 不要把卡片底部做成額外的「查看商品」整列。
- 外部連結 icon 應放在卡片上方商品品牌／來源資訊的右側，並沿用新原型的 icon 規範。

### 編輯與重複書籤

- 每筆書籤提供編輯入口，可修改商品名稱、圖片、品牌、價格與貨幣、顏色／款式、尺寸及備註，也可修正商品網址與其他已儲存資料。
- 編輯入口須與卡片的外部連結操作分開；操作編輯時不得意外開啟商品頁。
- 編輯後再次驗證必填欄位及圖片；更新成功後顯示最新資料。
- 允許同一商品網址建立不同顏色／款式或尺寸的多筆書籤，不得只以 URL 作為唯一鍵。
- 若使用者準備建立與自己現有書籤的商品網址、顏色／款式及尺寸皆相同的項目，在儲存前提醒可能重複，並提供「返回修改」及「仍要建立」；提醒不能阻止使用者明確選擇建立。

## 商品卡片內容

商品卡片至少顯示：

- 商品圖片
- 商品名稱
- 品牌（若有）
- 顏色／款式（若有）
- 尺寸（若有）
- 價格與貨幣（若有）
- 商品來源網域（若有）
- 外部連結 icon

建議顯示格式：

```text
商品名稱
品牌 · 顏色／款式 · 尺寸 M · NT$1,280 · brand.com
```

缺少選填資料時不要顯示多餘的分隔符號。

## 批次管理與刪除

刪除功能採用整個書籤頁面的批次管理模式，不提供卡片上的單筆垃圾桶按鈕。

管理模式需求：

1. 書籤列表頁提供「管理」入口。
2. 進入管理模式後，每張卡片顯示 checkbox 或等效的選取控制項。
3. 被選取的卡片要有明確視覺狀態。
4. 提供「全選／取消全選」。
5. 顯示目前選取數量。
6. 提供「刪除已選」按鈕。
7. 沒有選取任何項目時，刪除按鈕必須 disabled。
8. 刪除前顯示確認 dialog。
9. 刪除成功後清除選取狀態並離開管理模式。
10. 部分刪除失敗時：
    - 不要假裝全部成功。
    - 保留失敗項目為選取狀態。
    - 顯示明確錯誤訊息。
11. 管理模式下點擊卡片不應意外開啟商品外部連結。

## 資料模型

請依新專案既有資料庫與命名慣例實作。資料表可命名為 `wishlist_items`，每筆資料至少包含：

| 欄位 | 類型 | 必填 | 說明 |
|---|---|---:|---|
| `id` | UUID 或專案既有 ID 類型 | 是 | 書籤識別碼 |
| `owner_id` | 使用者 ID | 是 | 書籤擁有者 |
| `product_url` | string/text | 是 | 商品販售頁 URL |
| `title` | string/text | 是 | 商品名稱 |
| `image_url` | string/text | 條件必填 | 使用外部圖片時儲存其 URL；使用上傳圖片時可為空 |
| `image_storage_path` | string/text | 條件必填 | 使用上傳圖片時儲存檔案位置；使用外部圖片時可為空 |
| `brand` | string/text | 否 | 品牌 |
| `price` | string/text | 否 | 價格 |
| `currency` | string/text | 否 | 貨幣 |
| `variant_name` | string/text | 否 | 款式或 variant 名稱 |
| `color` | string/text | 否 | 使用者確認的顏色 |
| `size` | string/text | 否 | 使用者確認的尺寸 |
| `source_domain` | string/text | 否 | 商品來源網域 |
| `description` | text | 否 | 商品描述 |
| `notes` | text | 否 | 使用者備註 |
| `created_at` | timestamp | 是 | 建立時間 |
| `updated_at` | timestamp | 是 | 更新時間 |

圖片來源二擇一：每筆資料必須有有效的 `image_url` 或 `image_storage_path`，由系統依來源顯示圖片。上傳圖片的路徑不應依賴短期有效的簽署連結作為永久資料；依新專案既有儲存與存取權限設計實作。重複書籤採提醒而非資料庫唯一約束。列表依 `created_at` 由新到舊排序，時間相同時使用穩定次序。

### 權限

書籤是私人資料：

- 使用者只能讀取自己的書籤。
- 使用者只能新增自己的書籤。
- 使用者只能修改自己的書籤。
- 使用者只能刪除自己的書籤。
- 不能因為前端隱藏 UI 就省略後端權限驗證。

若新專案使用 Supabase，請建立對應的 RLS policies；若使用其他後端，套用等效的 owner-level authorization。

## 商品 metadata 解析

商品頁解析應在 server-side 執行，不要把需要保護的 API key 放到瀏覽器。

建議解析順序：

1. JSON-LD `Product`
2. Open Graph metadata，例如 `og:title`、`og:image`、`og:description`
3. Twitter Card metadata
4. HTML `<title>`
5. 商品 URL 的 host/path/filename 僅作為輔助，不可視為絕對正確

可解析的 JSON-LD 欄位包括：

- `name`
- `brand`
- `image`
- `offers.price`
- `offers.priceCurrency`
- `color`
- `size`
- `sku`
- `description`

注意：

- 不同品牌的商品頁格式不一致。
- 有些頁面需要 JavaScript 才會載入資料。
- 有些網站會阻擋 server-side request。
- 解析不到資料時，提供手動補充流程。
- 不要因為 metadata 解析失敗而建立缺少圖片的資料。
- 外部請求應設定 timeout、限制內容大小，並驗證 URL 協定。
- 防止伺服器請求偽造（SSRF）：拒絕指向 localhost、內部／私人網路位址或其他非公開目標的網址；DNS 解析及每次重新導向後都要重新驗證目標，並限制重新導向次數。若從伺服器抓取外部圖片，也須套用相同規則。

## 驗證與錯誤處理

至少處理以下情況：

- URL 空白
- 商品 URL 格式錯誤
- 商品 URL 使用非 `http`／`https` 協定
- 商品頁無法讀取
- 商品頁回傳非成功 HTTP status
- 找不到商品名稱
- 找不到商品圖片
- 圖片 URL 空白
- 圖片 URL 格式錯誤
- 圖片載入失敗
- 圖片上傳格式、大小不符或上傳失敗
- 已儲存的外部圖片日後失效
- 重複書籤提醒與使用者確認建立
- 編輯儲存失敗
- 使用者未登入
- 資料庫 migration 尚未執行
- 新增或刪除請求失敗
- 批次刪除部分成功、部分失敗

錯誤訊息應讓使用者知道下一步該做什麼，例如：

- 「找不到商品圖片，請貼上圖片網址或上傳圖片」
- 「圖片網址必須使用 http 或 https」
- 「商品頁無法讀取，請確認網址公開可存取，或手動補充資料」
- 「部分書籤刪除失敗，請再試一次」

## 空狀態與載入狀態

### 空狀態

沒有書籤時顯示：

- 尚未建立書籤的說明
- 建立書籤的主要 CTA
- 使用者貼上商品頁 URL 的簡短提示

### 載入狀態

以下操作要有 loading state，並避免重複提交：

- 讀取商品頁
- 儲存書籤
- 更新書籤及上傳圖片
- 批次刪除

## 實作順序

請依新專案架構調整，但建議順序如下：

1. 讀取新原型 HTML 與既有頁面元件。
2. 找到新專案的路由、狀態管理、API/server function 與資料庫方式。
3. 建立 `wishlist_items` 資料模型與 owner-level 權限。
4. 建立書籤列表頁與空狀態。
5. 建立商品 URL 表單與 metadata 解析流程。
6. 加入圖片必填、圖片 URL 驗證與圖片上傳。
7. 加入預設收合的「補充更多」區，包含顏色／款式／尺寸等選填欄位，確認收合不造成資料遺失。
8. 建立商品卡片與商品外部連結。
9. 加入編輯、重複書籤提醒、管理模式與批次刪除。
10. 依新原型進行 responsive、視覺與互動調整。
11. 補上測試並執行 lint、type-check、build。

## 驗收條件

功能完成前請確認：

- [ ] 書籤頁符合新原型 HTML 的視覺與 layout。
- [ ] 使用者可以貼上商品頁 URL。
- [ ] 商品 URL 只允許 `http`／`https`。
- [ ] 系統會嘗試自動取得商品基本資訊。
- [ ] 解析失敗時仍可手動補充。
- [ ] 商品名稱必填。
- [ ] 新增畫面先貼上網址，再以名稱及圖片為主要確認內容。
- [ ] 「補充更多」預設收合，點擊才展開非必填欄位，可再次收合。
- [ ] 不必展開或填寫選填區即可儲存符合必填要求的書籤。
- [ ] 選填資料在收合、儲存與編輯時完整保留；已填選填值驗證失敗時會展開定位錯誤。
- [ ] 有圖片時只顯示預覽與更換入口；缺圖時直接提供補圖入口。
- [ ] 每筆書籤有可用圖片，可使用圖片 URL 或上傳圖片。
- [ ] 使用圖片 URL 時必須是有效的 `http`／`https` URL。
- [ ] 圖片載入失敗時不能建立無圖書籤。
- [ ] 圖片上傳失敗時不能建立無圖書籤；既有外部圖片失效時可更換圖片。
- [ ] 表單中有顏色／款式欄位。
- [ ] 表單中有尺寸欄位。
- [ ] 卡片顯示圖片與可辨識款式的資訊。
- [ ] 點擊商品可開啟原商品頁。
- [ ] 可編輯既有書籤資料，且編輯操作不會誤開外部連結。
- [ ] 同網址可收藏不同款式／尺寸；完全相同的項目先提醒，再由使用者決定是否建立。
- [ ] 卡片底部沒有額外的「查看商品」操作列。
- [ ] 刪除採批次管理模式。
- [ ] 支援全選、取消全選與刪除確認。
- [ ] 批次刪除失敗時不會顯示成功假象。
- [ ] 使用者只能存取自己的書籤。
- [ ] 伺服器讀取外部網址時拒絕非公開目標，並檢查 DNS 與重新導向後的目標。
- [ ] 手機與桌面版都可正常使用。
- [ ] 相關測試、lint、type-check 與 production build 通過。

## 不要做的事情

- 不要把書籤資料混入已擁有的衣櫥單品資料。
- 不要只依圖片 URL 的檔名直接判定品牌或商品名稱。
- 不要只依商品 URL 判定使用者選擇的顏色、款式或尺寸。
- 不要在瀏覽器暴露 server-side API key。
- 不要讓 metadata 解析失敗時產生沒有圖片的書籤。
- 不要移除正式環境的登入與資料權限控制。
- 不要為了套用舊版本 UI 而覆寫新原型的設計。
